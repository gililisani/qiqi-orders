# Structural audit — 2026-08-02

Full-codebase audit triggered by finding two different "edit user" pages with
different capabilities. Five parallel read-only audits ran over: duplicate UI
flows, the API surface, the permission model, duplicated logic / dead code, and
data-access patterns.

Everything below was **verified by hand against the source** before being
written down. Claims that came back from an audit but did *not* survive
verification are listed in Part 6 so nobody re-raises them.

Excluded by prior decision: the known long files (`app/admin/dam/page.tsx`,
`PackingSlipView`, `OrderFormView`, `OrderDetailsView`, `companies/[id]/edit`)
are not flagged for size alone, and the accepted Supabase advisor warnings are
not re-litigated.

**Your instinct was right.** The two user-edit pages are not an isolated slip —
they're one instance of a pattern that repeats across the system: a feature gets
built, then a second version of it gets built somewhere else, and neither is
retired. There are 16 such pairs. Below that sits a more serious problem: the
permission system added in May is almost entirely cosmetic on the server.

## Part 1 — Fix first

These are live defects with business consequences, in the order I'd fix them.

### 1.1 Any logged-in user can read any order's customs paperwork (IDOR)

`app/api/orders/[id]/sli/data/route.ts:12-18` checks only that an
`Authorization` header is **present**, then passes the token to
`fetchOrderSLIData`. That helper (`lib/pdf/api/sliDataFetcher.ts:111-137`)
validates the token and then reads with the **service-role** client — no role
check, no company check.

Any authenticated distributor can request `/api/orders/<any-order-id>/sli/data`
and receive another company's Shipper's Letter of Instruction: consignee,
addresses, declared values, HS codes. The sibling route
`app/api/orders/[id]/sli/route.ts:26-54` *does* check company ownership — that's
what this one should look like.

The endpoint is live (used by `app/admin/orders/[id]/sli-preview/page.tsx:62`).

**Fix:** `requireAuthenticatedUser` + `assertOrderAccess`, or `requireAdmin` to
match the rest of the SLI family.

### 1.2 Every new user is created with zero permissions

`app/api/users/create/route.ts:79-85` calls the `create_client_profile` RPC with
name/email/company/enabled only. The RPC
(`supabase/migrations/20260514120000_user_lifecycle_rpcs.sql:33-34`) doesn't
write `permissions`, and the column defaults to an empty array
(`supabase/migrations/20260526120000_user_permissions.sql:33,36`).
`DEFAULT_CLIENT_PERMISSIONS` in `lib/permissions.ts:47` is referenced only by the
edit page's form state — never by any creation path.

So every client user created since the May permissions migration lands with `[]`,
logs in, and gets bounced to `/forbidden` (`app/client/layout.tsx:182-192`). The
account only starts working if someone happens to open `/admin/users/[id]/edit`
and save, which re-grants defaults as a side effect (see 1.6).

Same bug for admins: `app/api/admin/create/route.ts:88-95` inserts without
permissions, while `app/admin/admins/new/page.tsx:97-103` tells the operator
"This admin will have full access to the system." The new admin gets an empty
sidebar instead.

**Fix:** write the defaults at creation time (or change the column default).

### 1.3 Permissions are not enforced on the server

`requireWithPermission` exists in `platform/auth/guards.ts:90` and is called by
exactly **one** route out of 95: `app/api/client/performance/route.ts:24`.
Everything else stops at "is this an admin" / "is this a client".

Meanwhile the admin area has **no route guard at all** — `app/admin/layout.tsx`
filters nav items but never redirects, unlike `app/client/layout.tsx:182-193`.
So an admin restricted to, say, DAM reaches every admin page by typing the URL,
and every admin API answers them. Today `users:manage`, `admins:manage`,
`companies:manage`, `netsuite`, `settings` and `reports` have no server-side
effect whatsoever.

Worse, permission writes happen **from the browser**:
`app/admin/admins/[id]/edit/page.tsx:79-88` updates `admins.permissions`
directly, and the RLS policy
(`supabase/migrations/20260515120000_tier1_rls_overhaul.sql:68-71`) only asks
"are you an admin". Any admin can grant themselves everything.

**Fix, staged:** (a) port the client layout's redirect guard into the admin
layout; (b) move the two permission writes behind guarded API routes; (c) convert
route families to `requireWithPermission`.

### 1.4 Disabling a user does not lock them out

`app/api/user-profile/route.ts:91-102` returns the profile and role regardless of
`enabled`, and `app/client/layout.tsx:153` checks only the role. Supabase Auth
doesn't know about `enabled`, so a disabled user still authenticates and still
gets the portal shell.

Most data comes back empty because `auth_company_id()` requires `enabled = true`,
so it *looks* like an empty account rather than a revoked one — but the session
is real, and any table whose policies don't check `enabled` stays readable.

**Fix:** reject `enabled !== true` in the layout and in `/api/user-profile`.

### 1.5 Target-period progress is never recalculated when an order completes

Two callers hit `/api/target-periods/recalculate` with plain `fetch` and no
Authorization header:
`app/components/shared/orderDetails/useOrderDetailsController.ts:222-226` (fires
when an order flips to/from Done) and
`app/admin/companies/[id]/historical-sales/page.tsx:97-101`.

The token lives in localStorage, not cookies, so `requireAdmin` rejects both.
Both callers swallow the failure — one logs, one has an empty catch. The stored
`current_progress` silently stops tracking reality while the UI reports success.
This is the same shape as the missing `order_history` writes that hid $265k of
Done orders in July.

**Fix:** use `fetchWithAuth`, and surface failures instead of swallowing them.

### 1.6 The permissions editor silently re-grants defaults

`app/admin/users/[id]/edit/page.tsx:72-74` and
`app/admin/admins/[id]/edit/page.tsx:53-55` both do "if the stored array is
empty, show the defaults". Deliberately removing every permission is therefore
not representable: reopen the page and the boxes are ticked again, and saving any
unrelated field re-grants `['orders','dam']` — or, for admins, all eight
permissions including `admins:manage`.

**Fix:** use the stored array verbatim once loaded; seed defaults only on create.

### 1.7 Changing an admin's email or password silently does nothing

`app/admin/admins/[id]/edit/page.tsx:91-101` calls
`supabase.auth.admin.updateUserById` from a **browser** page using the anon key.
That API needs the service-role key, so it always fails — and the result is never
checked, so the page reports "Admin updated." The profile row changes; the actual
login credentials don't, so the user's login email silently diverges from their
displayed email.

The same unchecked call was copy-pasted into all three user-edit pages
(`app/admin/users/[id]/edit/page.tsx:107-112`,
`app/admin/companies/[id]/users/[userId]/edit/page.tsx:86-91`).

**Fix:** one guarded API route doing profile + auth atomically.

### 1.8 Client "delete order" calls an endpoint that doesn't exist

`app/components/client/ClientOrderDetailsView.tsx:160` does
`DELETE /api/orders/${orderId}`. There is no `route.ts` at that path — only
`documents/` and `sli/` children. The real endpoint is `/api/orders/delete?orderId=`,
used correctly by the admin controller (`useOrderDetailsController.ts:518`).
Deleting from the client portal always fails with "Failed to delete order."

Three different rules for this one action also coexist: the API allows any role
on Cancelled only; the shared controller says Cancelled-or-Draft with Cancelled
admin-only; the client view shows the button on Cancelled.

### 1.9 Clients can edit packing slips

`app/components/shared/PackingSlipView.tsx:840` gates editing on order status
only — `['Ready','Done'].includes(order.status)` — with no role check, even
though both pages pass a `role` prop. On `/client/orders/[id]/packing-slip` a
distributor gets working Create/Edit affordances on a shipping document
(invoice number, NetSuite reference, notes).

**Confirmed against production RLS (3.3): the database permits the write.** This
is real edit access, not a button that fails.

**Fix:** `role === 'admin' && [...]`, and tighten the policy to SELECT for
clients.

### 1.10 Order writes don't check that anything was written

`app/components/shared/orderForm/useOrderFormController.ts:251-275` updates the
order, deletes its items and re-inserts — with no `.select()` and no row count.
supabase-js returns `error: null` when RLS filters an UPDATE to zero rows, so a
blocked write is indistinguishable from a successful one. If an admin moves an
order to Processing while a client has the form open, the client's save no-ops
and the UI redirects as though it saved.

### 1.11 New companies are invisible to target-based reporting

`app/admin/companies/new/page.tsx:183-215` inserts 26 columns but omits
`contract_execution_date`, `contract_duration_months` and `contract_status`, and
has no territories or target-periods editors — all of which exist only in
`app/admin/companies/[id]/edit/page.tsx:388-427`.

Since `target_periods` is what drives `lib/companyPerformance.ts`, every company
onboarded through the create form is absent from Company Performance until
someone remembers to reopen it in Edit.

### 1.12 Bulk-uploaded products get wrong support-fund behavior

`app/admin/products/bulk-upload/page.tsx:128-145` writes 13 columns. It never
writes `category_id`, `qualifies_for_credit_earning`, `hs_code`, `made_in`,
`case_weight` or `out_of_stock` — the words don't appear in the file at all,
while both single-product forms write 18 columns.

Consequences: imported SKUs have no category (so they don't group in the order
form), no HS code or weight (SLI and packing-slip fields), and fall to the DB
default for credit earning — which feeds support-fund accrual
(`AdminOrderFormView.tsx:447`) and therefore money.

## Part 2 — The duplication pattern

This is the direct answer to "why are there two edit-user pages". There are 16
of these. The ones that matter:

**Two "edit user" pages.** `app/admin/users/[id]/edit/page.tsx` (294 lines) has
permissions *and* company reassignment.
`app/admin/companies/[id]/users/[userId]/edit/page.tsx` (231 lines) has neither.
Both are live; neither links to the other. The Users list routes to the capable
one; `app/admin/companies/[id]/page.tsx:537` — the Edit button on every user row
of a company, the path you'd naturally use — routes to the crippled one. They
even send different reset-link payloads, so the two produce different emails.

**Two "create user" pages** (`app/admin/users/new`, `app/admin/companies/[id]/users/new`)
— these at least both post to `/api/users/create`.

**SLI is two entities with two form systems and three preview pages.** Order SLIs
live in `slis`, standalone SLIs in `standalone_slis`. The standalone form
(`SLIFormFields.tsx`, 686 lines) exposes all 19 checkbox groups; the order form
(`CreateSLIModal.tsx`) hardcodes five of them with no setter
(`CreateSLIModal.tsx:64-82`). Order SLIs get no SLI number and **never appear in
the SLI documents list**, which queries `standalone_slis` only
(`app/admin/sli/documents/page.tsx:23-26`) — customs paperwork issued against
orders is untracked. Three preview pages render it three ways, one of which
(`/admin/sli/preview`) has zero references anywhere.

**Order create/edit is forked admin↔client**, ~2,500 lines, with eleven helper
functions duplicated character-for-character including `getProductPrice`,
`getOrderTotals` and `getSupportFundTotals`. Any pricing change has to land in
two files or admin-entered and client-entered orders price differently. Both
sides also declare `visible_to_americas`/`visible_to_international` and use
neither, so region visibility silently does nothing.

**Order details / list / documents / history are each forked** the same way —
`AdminOrderHistoryView` and `ClientOrderHistoryView` are ~99% identical and the
client file's own comment admits the visual is identical.

**Company create vs edit** duplicate a 26-column mapping character-for-character
(see 1.11). **Product create vs edit vs bulk-upload** are three payloads (see
1.12). **DAM locale/tag creation exists twice** with different validation — the
inline path in `app/admin/dam/page.tsx:3316` uses `prompt()`/`alert()` and skips
the duplicate check the settings page has. **Category ordering is editable two
ways** with incompatible semantics: a curated `sort_order` set in the edit form
is wiped the next time anyone saves the drag-and-drop reorder page.

**Three admin-auth implementations coexist**: `requireAdmin`,
`createAuth().requireRole`, and hand-rolled `admins` lookups — the last is where
the IDOR in 1.1 slipped through. Plus ~18 hand-rolled service-role clients
instead of `createServiceRoleClient()`.

## Part 3 — RLS: resolved, and worse than expected

**Resolved:** the ten tables I couldn't find policies for all have them — added
via the Supabase dashboard, which is why they're absent from
`supabase/migrations/`. Clients are **not** silently seeing empty notes,
documents, history or territories. RLS is enabled on every table in `public`.

Reading the live policy bodies surfaced five real problems that were invisible
from the code alone. Ranked:

### 3.1 Clients can modify and delete order documents

```
client_delete_company_documents  DELETE  company match only
client_update_company_documents  UPDATE  company match only
client_upload_company_documents  INSERT  company match only
```

No status check, no ownership check beyond company. A distributor can **delete
the invoice PDF an admin uploaded** to their order. Destructive and live.

### 3.2 The `is_public` flag on order documents does nothing

Two SELECT policies are OR'd: "Clients can view public documents for their
orders" (`is_public = true`) and `client_view_company_documents` (company match,
no `is_public` condition). The second makes the first irrelevant — clients see
**every** document on their company's orders, including ones marked internal.

### 3.3 Clients can edit packing slips — for real

`Clients can access their packing slips` is `FOR ALL` with a matching
`WITH CHECK`, scoped only by company. So finding 1.9 is not a button that fails:
`PackingSlipView.tsx:840`'s missing role check exposes genuine write access to
shipping documents (invoice number, NetSuite reference, notes).

### 3.4 A leftover policy defeats the May permission system on `order_items`

`order_items_client_write` (`FOR ALL`, from the tier-1 overhaul) checks company
and order status but **not** `auth_has_permission('orders')`. The four newer
policies from the permissions migration all check it. Policies are OR'd, so the
old one wins: **revoking a client's `orders` permission does not stop them
writing order items.**

`orders` itself looks clean — its five policy names all come from the permissions
migration — but I have not read its bodies; worth confirming in the same pass.

### 3.5 Disabled admins keep admin access

The older dashboard policies test `EXISTS (SELECT 1 FROM admins WHERE admins.id =
auth.uid())` with **no `enabled = true`**. That pattern is on `order_documents`
(all four admin policies plus `admin_full_access`), `packing_slips`, `slis`,
`order_history`, and `clients` ("Admins can view all clients"). The newer
`auth_is_admin()` helper does check `enabled`.

Combined with finding 1.4 — disabling a user doesn't prevent login — **disabling
an admin is largely cosmetic**: they can still sign in, read every client record,
and read/write order documents, packing slips, SLIs and order history.

### 3.6 Clients can write arbitrary order-history rows

"Clients can insert order history for their company" constrains only the company
link — not `status_to`, `role`, or `notes`. A client can insert a row claiming a
status transition that never happened. Since `lib/companyPerformance.ts` derives
each order's Done date from `order_history`, a forged row can shift revenue
between target periods, and the audit log stops being trustworthy.

### 3.7 `orders` is clean (verified)

All five `orders` policies check both `auth_company_id()` and
`auth_has_permission('orders')`. No leftover. That isolates `order_items` as the
single table where the permission gate is defeated — and note the leftover
`order_items_client_write` is `FOR ALL`, which includes SELECT, so revoking a
client's `orders` permission doesn't even hide their line items.

### 3.8 DAM entitlement is enforced only in the API — the database grants every authenticated user the whole catalog

`dam_assets_read_authenticated` is `USING ((NOT is_archived) AND (auth.uid() IS
NOT NULL))`. Any logged-in user can read **every non-archived asset**. The same
blanket-authenticated read is on `dam_asset_audience_map`, `dam_asset_locale_map`,
`dam_asset_region_map`, `dam_asset_renditions`, `dam_asset_tag_map`,
`dam_asset_versions`, and on the taxonomy tables `dam_audiences`, `dam_locales`,
`dam_regions`, `dam_tags` (those with a bare `auth.uid() IS NOT NULL`).

So a distributor can query `dam_assets` straight from the browser and get the
full catalog — **including `dam_asset_audience_map`, which is the map of who is
entitled to what**. The company-scoping model (`company_dam_audiences`,
`list_client_dam_assets_entitled`, `/api/dam/assets/client`) lives entirely at
the API layer and is bypassed by a direct query.

Files themselves stay protected: `/api/assets/[id]/download` and `/preview` check
entitlement via `platform/auth/damAssetAccess.ts`. What leaks is metadata — asset
names, descriptions, campaigns, product lines, region/audience targeting. For a
business with exclusive-territory distributors, that's competitor-visible
information about other regions and unreleased products.

### 3.9 One policy has no authentication check at all

`dam_job_queue_read` is `USING (true)` — the only unconditional policy in the
database.

Not publicly reachable, as it turns out:
`20260516120000_revoke_anon_and_bucket_listing.sql:20` does
`REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon` (plus a matching
`ALTER DEFAULT PRIVILEGES`), so `anon` holds no SELECT grant. The policy is
therefore readable by any **authenticated** user rather than the public — still
wrong, but not an anonymous leak. Tighten it anyway.

### 3.10 Two admin-check functions, and the DAM one can't run in a browser session

The DAM tables' admin policies call `is_admin()`; everything from the tier-1
overhaul calls `auth_is_admin()`. They are different functions:

- `auth_is_admin()` (`20260515120000_tier1_rls_overhaul.sql:19-27`) checks
  `enabled = true`, and `authenticated` has EXECUTE.
- `is_admin()` had EXECUTE **revoked from `authenticated`**
  (`20260514210000_lock_down_definer_functions.sql:16`), and its body is not in
  any migration, so whether it checks `enabled` is unverified.

Consequence: every `dam_*_admin_full` policy is effectively inert for browser
sessions — an admin's direct query can't even evaluate it. DAM admin work only
functions because all of it routes through service-role API routes. The single
effective browser-session policy on those tables is the blanket authenticated
read in 3.8.

Also minor: `dam_download_events_user_insert` has
`WITH CHECK (auth.uid() IS NOT NULL)`, so any authenticated user can write
arbitrary rows into the download audit log — matching the API-side finding that
`/api/dam/downloads/log` accepts any authenticated caller.

### 3.11 Documentation drift

`CLAUDE.md` states `note_replies` is admin-only. It isn't — clients can select
and insert, correctly scoped to `visible_to_client` notes of their own company
with `enabled = true`. The policy is fine; the documented posture is stale and
should be corrected so the next change isn't made on a false premise.

### Policy sprawl, generally

Old dashboard policies were never dropped when migrations added new ones:
`order_documents` has 10 policies, `order_items` and `slis` have 6, `clients` has
4 with obvious duplicates. Because permissive policies are OR'd, every stale one
is a silent hole in whatever the newer policy was meant to tighten — 3.2 and 3.4
are exactly that failure. Any cleanup migration should **drop the superseded
policies by name**, not just add better ones.

## Part 4 — Consistency debt

Not urgent, but it's what turns a one-line change into a three-file change and
lets copies drift apart.

- **Order status has six sources of truth** — two colour maps
  (`components/qq/status-badge.tsx:31`,
  `admin/reports/_components/StatusFunnelChart.tsx:12`) that disagree with each
  other, a third dead one, `STATUS_ORDER`/`COMMITTED_STATUSES` in the executive
  report route, and ~20 open-coded membership tests.
- **Currency formatting has ten implementations** — some 0-decimal, some
  2-decimal, one emitting `US$` — plus ~20 raw `.toFixed(2)` sites that lose
  thousand separators, so the same amount renders `$12,345.67` in one place and
  `$12345.67` in another. `lib/formatters.ts:31` is the canonical one.
- **Date formatting has eight local `formatDate` copies** in three formats, plus
  ~25 bare `toLocaleDateString()` calls that render `dd/mm/yyyy` for non-US
  browsers. Some pin UTC, some don't — those can be off by a day.
- **`lib/csvExport.ts:173`** wraps CSV fields in quotes without doubling embedded
  quotes, so a name containing `"` corrupts the NetSuite import file.
  `lib/reportExport.ts:96` does it correctly.
- **`userHasPermission` (`lib/permissions.ts:74`) has zero callers** despite its
  own doc saying "use this everywhere". Consequence: the `SUPER_ADMIN_IDS`
  override works for API routes but not for nav filtering or client-side gating —
  and it's parsed twice, in two places, with different semantics.

## Part 8 — The money path: NetSuite and Stripe

Audited 2026-08-02 in the second sweep. **This section outranks everything else
in this document.** Findings here were verified by hand; where the two auditors
disagreed with each other I read the code myself and my reading is what's below.

### 8.1 CRITICAL — A client can set their own prices, and those prices become the NetSuite invoice

The single most serious finding in this audit.

- `app/components/client/ClientOrderFormView.tsx:263,273` builds each
  `order_items` row with a browser-computed `unit_price`.
- `app/components/shared/orderForm/useOrderFormController.ts:174` inserts those
  rows **directly from the browser** with the anon key. The same file writes
  `orders.total_value` at `:190,210,256,292`.
- RLS permits it: `order_items_client_insert/update` allow writes whenever the
  parent order is in the client's company and its status is `Draft` or `Open`.
  **Postgres RLS cannot restrict *which columns* are written** — that needs
  column-level `GRANT`s, and I verified there are none in any migration. No
  `CHECK` constraint on `unit_price`, no trigger. (The only `unit_price > 0`
  check in the schema is on the unrelated `amazon_item_map` table.)
- Nothing re-derives price server-side. `app/api/netsuite/push-so/route.ts:50`
  merely *selects* `unit_price`, and `lib/netsuite.ts:393` uses it directly as
  the Sales Order line `rate`.

So a client with the `orders` permission can post `unit_price: 0.01` to their own
Draft order, the admin clicks Push, and NetSuite — the accounting system of
record — issues a Sales Order and then an Invoice at that price. The Stripe
charge is then anchored to that invoice.

This requires deliberate action (a crafted request, not the UI), and it needs the
`orders` permission. But it is reachable by every client user today and there is
no server-side check anywhere in the chain.

**Fix:** re-resolve every line's rate server-side in `push-so` from `Products` ×
the company's class, and reject or repair any order whose stored `unit_price`
disagrees. Longer term, move order writes behind a service-role API route so the
browser never writes price columns at all (this is the same fix as audit 1.10).

### 8.2 CRITICAL — Voiding a payment request clears local state even when Stripe refuses

`app/api/stripe/void-payment/route.ts:42-46` catches a `voidInvoice` failure,
logs `(continuing)`, and proceeds. Line 68 then unconditionally nulls
`stripe_invoice_id`, `stripe_hosted_url` and `payment_status`.

The paid-check at `:33` reads `order.payment_status`, which is only ever set by
the webhook. So: webhook missed → local still says `pending` → admin clicks Void
→ Stripe rejects it (already paid) → error swallowed → the Hub forgets the
invoice ever existed, and `:59` also strips the credit-card fee line off the
NetSuite invoice. The customer's real payment is now unattributable and NS AR is
short by the fee.

**Fix:** retrieve the invoice from Stripe and refuse to void anything already
captured; only clear local columns when the void actually succeeded.

### 8.3 CRITICAL — A failed database write after a successful charge is silent

`app/api/stripe/webhook/route.ts:78-86` updates the order **without checking the
result**. supabase-js does not throw on a failed write — it returns `{ error }`.
So a failed update does *not* reach the catch at `:98`, does *not* return 500,
and Stripe never retries. The endpoint returns `{ received: true }` while the
order stays `pending` forever and the NetSuite Customer Payment has already been
recorded at `:69`.

Note both auditors described this differently and neither was quite right — the
comment at `:99-104` reasons about retry behaviour that cannot occur, because the
only statement that could throw is the NetSuite call, and that one is already
caught at `:72`.

The same unchecked-write pattern is in
`app/api/stripe/request-payment/route.ts:169-183`, which is worse: the Stripe
invoice has already been **created, finalised and emailed** at `:153-163`. If the
persist fails, the customer holds a live payment link the Hub has no record of.
Clicking the button again passes the `:63` guard (because `stripe_invoice_id` was
never stored) and creates a **second** invoice — and there is no Stripe
idempotency key anywhere in `lib/stripe.ts`.

**Fix:** check every write's error; write the intent row *before* calling Stripe;
pass `idempotencyKey: \`order-${orderId}-invoice\`` on invoice creation.

### 8.4 HIGH — No reconciliation between Stripe and the local database

`lib/stripe.ts:131` `getInvoice()` has zero callers. No cron reconciles payments
(`vercel.json` has crons only for Amazon FBA and reports).
`/api/netsuite/refresh-all-invoices` never touches `payment_status`.

If the webhook is missed for any reason — endpoint misconfigured, deploy window,
Stripe exhausting its retries — the order sits `pending` permanently. The client
sees "Pay Now" on an order they already paid, NS shows an open invoice, and
nothing surfaces it. A paid invoice with no matching order also exits silently:
`webhook/route.ts:51-55` uses `maybeSingle()` and falls through to a 200.

**Fix:** a cron that retrieves Stripe invoices for every `payment_status='pending'`
order and applies the paid transition through the same code path; alert loudly on
a paid invoice with no matching order.

### 8.5 HIGH — No handling for refunds, chargebacks, or failed payments

`webhook/route.ts:45` handles only `invoice.paid` and
`invoice.payment_succeeded`. There is no `charge.refunded`,
`charge.dispute.created`, `invoice.payment_failed`, `invoice.voided`, or
`invoice.marked_uncollectible`, and no refund code path exists anywhere. Money
refunded or charged back in Stripe leaves the Hub and NetSuite both showing
**Paid in Full**, and the order continues to fulfilment.

Related: `app/api/fulfillment/shiphero/push/route.ts` never checks
`payment_status`, even though the client UI says "Payment is required to release
this order." An unpaid order can be pushed to the 3PL and shipped.

### 8.6 HIGH — NetSuite is marked paid in full without comparing what Stripe collected

`webhook/route.ts:69` calls `recordCustomerPayment(invoiceId, accountId)`, which
applies the **full outstanding invoice balance** (`lib/netsuite.ts:656-687`). The
event object is typed as `{ id?: string }` at `:46` and `amount_paid` is never
read. The webhook also hard-writes `invoice_amount_remaining: 0` at `:83`.

Whenever the Stripe charge is smaller than the NetSuite balance — which the
fallback in 8.7 makes possible — NetSuite books a full payment for money that was
never received.

### 8.7 HIGH — Silent fallback when NetSuite omits the invoice total

`app/api/stripe/request-payment/route.ts:131`:
`const nsTotal = details.amountRemaining ?? feeBase + fee;`

`lib/netsuite.ts:705-718` returns `amountRemaining: null` whenever the REST
record omits the field, and `findInvoiceForSalesOrder` returns null by design.
The fallback silently charges the Hub-local total, which excludes tax and any
NetSuite-side pricing difference — then 8.6 marks the NS invoice fully paid
anyway. No log, no warning.

Also at `:148`: `goodsCents = totalCents − shippingCents − feeCents` has no floor,
so an order largely covered by support-fund credit can produce a negative goods
line or a $0 invoice. A finalised $0 Stripe invoice is immediately `paid` and
emits `invoice.paid`, flipping the order to Paid in Full and recording a NetSuite
payment for money never charged.

**Fix:** hard-fail when `amountRemaining` is null; reject when `nsTotal <= 0`.

### 8.8 HIGH — Other NetSuite correctness findings

- **Deleting a paid invoice is possible.** `lib/netsuite.ts:788-797`
  (`getInvoicePayments`) queries the transaction link in the *opposite*
  direction from `getInvoicePaymentsDetailed` at `:836-847`, whose comment says
  it was verified against the real account. The verified one has **zero callers**;
  the unverified one backs the only guard preventing deletion of an invoice with
  money applied (`app/api/orders/delete/route.ts:84-92`). It returns `[]`, the
  guard passes, and a settled AR transaction can be deleted.
- **Re-push silently links a stale Sales Order.** `lib/netsuite.ts:348` returns
  any SO matching `externalId` *before* comparing contents. Unlink → edit → Push
  reports "Sales Order created" while NetSuite still holds the pre-edit lines, so
  the customer is invoiced for the old quantities.
- **`removeInvoiceChargeLine` rewrites the whole invoice sublist** from a
  four-field projection (`lib/netsuite.ts:585-632`), dropping
  `inventorylocation`, `description`, `taxcode`, `class` and `department`, and
  deleting any line without an `item.id`. Used by the shipping and void paths.
  On a cross-subsidiary invoice this breaks intercompany posting.
- **Shipping revenue can be silently dropped.**
  `app/api/netsuite/create-invoice/route.ts:95-103` wraps the shipping-line
  upsert in a `console.error`-only catch, then returns `{success: true}`. The
  customer is billed short with only a server log as evidence.
- **`push-so` reports success when the local write fails** (`:108-111`, with a
  comment saying so), and has **no order-status gate** — a direct POST can push a
  Cancelled or Draft order into NetSuite.
- **No unique index on `orders.netsuite_so_id` / `netsuite_invoice_id`**, so
  `reconcile-order` can link two Hub orders to one NetSuite SO and double-count
  revenue.
- **`tranDate` is UTC-derived** (`lib/netsuite.ts:447`) while the CSV path uses
  local date — an order placed after midnight Israel time books into the previous
  month, and into a closed period at year end.
- **Support-fund discount item is resolved by hardcoded name**
  (`lib/netsuite.ts:425`, `'partners support funds'`) instead of via
  `netsuite_item_map`. Renaming it in NetSuite breaks every support-fund push
  until a code deploy.

### 8.9 Zero test coverage on the entire money path

`tests/` contains no match for `stripe` or `payment`, and NetSuite coverage is
exactly one function (`normalizeNsDate`). Untested: the SO payload builder, the
support-fund line algebra, the fee arithmetic, cents conversion, the goods-line
subtraction, webhook signature handling and idempotency, and every void guard.
Every finding in this section is invisible to CI.

`pushOrderToNetSuite` is a pure function of its inputs once `resolveItemIdsBySku`
and `suiteQL` are mocked — a snapshot test of the payload is the single
highest-value test file to add.

### 8.10 Verified correct — don't spend time re-checking

- Stripe webhook signature verification uses the raw body
  (`await request.text()` → `constructEvent`) and 400s correctly. `dynamic =
  'force-dynamic'` is set. `/api/stripe/*` is deliberately outside the middleware
  matcher.
- No Stripe secret reaches a client bundle; `lib/stripe.ts` is imported only by
  the three Stripe routes and one server-side dynamic import.
- The client cannot set the charge amount directly — the only request field is
  `orderId`. (It can influence it indirectly via 8.1.)
- The credit-card fee arithmetic is correct: `Math.round(feeBase * feePercent)`
  yields cents because dollars × percent = cents. No float money is stored.
- NetSuite OAuth 1.0a TBA signing is correct, and there is **no HTTP-layer retry
  anywhere**, so retries cannot duplicate writes.
- `externalId = order.id` plus the post-failure re-check is a sound duplicate-SO
  design; `recover-so` cannot create a duplicate.
- Case-pack conversion happens exactly once, at form time. `order_items.quantity`
  is already in units and NetSuite receives units — no double conversion.
- Amazon FBA batch claiming (`UNIQUE(period)` + `pushing` status) is the
  strongest idempotency in the codebase.

### 8.11 Documentation gap

Stripe card payments are **fully built and live** — three routes, admin and
client UI, three applied migrations, six feature commits. `CLAUDE.md` does not
mention Stripe at all, and project memory recorded it as "designed, not built."
Both need correcting; an agent reading the current docs would not know this money
path exists.

## Part 9 — Order money math

### 9.1 CRITICAL — All order money is computed in the browser and written directly

Same root cause as 8.1, stated from the money side.
`useOrderFormController.ts:187-194,251-260` writes `total_value`,
`support_fund_used` and `credit_earned` straight from browser state via the
anon-key client. `orders_client_update`'s `WITH CHECK` constrains only
`company_id` and status — **every other column is writable**, and RLS cannot
restrict columns.

Worked example: a client places a real $10,000 order (tier 10%, earned $1,000),
then from devtools runs
`supabase.from('orders').update({support_fund_used: 9000, total_value: 1000})`.
`lib/netsuite.ts:424-443` reads `support_fund_used` verbatim and posts a
`Partners Support Funds` line at `rate: -9000`. The cap at
`useOrderFormController.ts:183` never runs on that path.

**Fix:** recompute totals server-side (trigger or RPC) from `order_items` ×
`Products`, and revoke client UPDATE on the money columns.

### 9.2 HIGH — `case_pack = 0` from bulk upload under-bills by the whole case factor

`app/admin/products/bulk-upload/page.tsx:134` writes
`parseInt(...) || 0` — a blank or malformed cell stores **0**. Both order forms
then do `quantity = caseQty * (product.case_pack || 1)`
(`AdminOrderFormView.tsx:376,410`, `ClientOrderFormView.tsx:336,367`), and `0` is
falsy, so it silently becomes **1**.

Worked example: a SKU imported with a blank case-pack cell, real pack of 12, unit
price $10. The client orders 3 cases expecting 3 × 12 × $10 = **$360**. The form
computes 3 units, `total_price = $30`, displays "Case Pack 0", saves 3 units, and
NetSuite receives `quantity: 3`. **$30 billed and 3 units shipped instead of $360
and 36 units.**

This compounds with audit 1.12 (bulk upload doesn't write `category_id` or
`qualifies_for_credit_earning` either).

**Fix:** `NOT NULL CHECK (case_pack > 0)`, make the field required in
`ProductFormFields`, and replace the `|| 1` fallbacks with a hard error.

### 9.3 HIGH — Item-level reports count free support-fund goods as revenue; order-level reports don't

`orders.total_value` **excludes** redeemed support-fund goods
(`useOrderFormController.ts:184-185` adds only the amount above `credit_earned`).
But every item-level revenue path sums `order_items.total_price` with no
`is_support_fund_item` filter — verified:

- `app/api/reports/product-insights/route.ts:91` doesn't even select the column;
  revenue at `:116`, heatmap at `:321`.
- `supabase/migrations/20260524120000_executive_dashboard_mvs.sql:89` —
  `mv_product_sales.revenue = SUM(oi.total_price)`, while `mv_daily_sales` and
  `mv_company_sales` use `SUM(total_value)`.
- `lib/companyPerformance.ts` filters on `is_support_fund_item` only at `:495`,
  the support-fund-specific query — not for `window.topProducts` / `window.units`.
- `app/api/reports/sales-explorer/route.ts:151` (pivot cells) vs `total_value` at
  `:137`.

Worked example: one Done order — $10,000 regular, tier 10%, client redeems
exactly $1,000 of support-fund product. `total_value = $10,000`. Company
Performance shows `window.sales = $10,000` while its own Top Products table on
the same screen sums to **$11,000**, and `units` counts the free cases.

At ~$2M/yr with 8–10% tiers, that is a systematic **8–10% overstatement** in
every product, category and subsidiary revenue view relative to the order list.

**Fix:** add `.eq('is_support_fund_item', false)` to those queries and to
`mv_product_sales` — or define the metric as gross-of-credit and label it that way
everywhere. Pick one and make it explicit.

### 9.4 MEDIUM-HIGH — Order detail can never show unused support-fund credit

`ClientOrderDetailsView.tsx:207` and `AdminOrderDetailsView.tsx:1558` compute
`balance = support_fund_used − supportSubtotal`. Since `support_fund_used` is
already `min(claimed, earned)`, that expression is **0 whenever the client
under-redeems**. The documented model (and the Support Funds report) is
`balance = credit_earned − claimed`.

Worked example: tier 10%, $10,000 qualifying → earned $1,000. Client redeems
$300. The order page prints **Balance $0.00**; the Support Funds report prints
**$700** leftover for the same order.

**Fix:** use `credit_earned` in both detail views.

### 9.5 MEDIUM — Other verified money defects

- **Non-atomic save in the wrong order.** `useOrderFormController.ts:251-275`
  updates `total_value`, then deletes items, then re-inserts. A failed insert
  leaves a priced order with **zero line items** — counted at full value in
  revenue, pushed to NetSuite as an SO with no lines. The create path can leave
  `total_value = NULL`, displayed as $0.00.
- **Editing re-prices only touched lines.** Existing lines keep their stored
  price while any line whose quantity changes re-prices from today's product
  master, so one order ends up on two price bases, and `credit_earned` is
  computed over the mixture.
- **Money is never rounded on write.** No `Math.round` anywhere in the write
  path; `credit_earned` persists as e.g. `451.5792` and goes to NetSuite as
  `rate: -451.5792` and to Stripe as the fee base, while the UI shows `$451.58`.
- **Packing slip re-derives case counts** from the current product master
  (`PackingSlipView.tsx:571,686,693,1242,1269`) instead of using the stored
  `case_qty`, so changing a product's case pack retroactively changes what the
  shipping document says was shipped — including total weight.
- **Order confirmation emails don't reconcile.** `send-email/route.ts:93-101`
  lists all items at full price including support-fund lines, then shows
  `total_value` as the total, with no discount row and no shipping row. The lines
  visibly don't sum to the stated total.
- **The support-fund badge on the orders list** shows redemption-over-total
  labelled as the tier percent, so a 10% company can display "5% SF" — or
  "50000% SF" when `total_value` is 0.
- **SLI customs values ignore the buyer's price class** and include free
  support-fund goods at list price, so a $10,000 commercial invoice can be
  declared at $11,000.

### 9.6 SUSPECTED — the pricing fallback is still the sharpest edge

`AdminOrderFormView.tsx:344-348` / `ClientOrderFormView.tsx:306-310`:
`className.includes('america') ? price_americas : price_international`.

Three ways it silently defaults wrong: the `class` embed resolves to `null` (the
client form defensively unwraps array-vs-object for `company` and `support_fund`
but **not** for `class`); RLS returns null for `classes` when `auth_company_id()`
is null, which also zeroes `supportFundPercent`; or someone names a class "USA
Distributors" or "Domestic", which doesn't contain "america".

Worked example: a North America client whose class row is unreadable orders
100 cases × 12 at $12 americas vs $10 international — invoiced **$12,000 instead
of $14,400**, with `credit_earned` $0 instead of $1,440, and no warning anywhere.

This is the exact shape of the May 2026 pricing bug, and there is still no
regression test for it. Recommended fix: resolve the price column from a stored
enum on `companies` (or a `classes.price_tier` column) and **throw** rather than
defaulting when it can't be resolved.

## Part 10 — DAM pipeline and storage

**Important caveat: `supabase/migrations/` contains no `storage.objects` policy
or bucket definition at all.** The bucket-creation SQL exists only in deleted
files in git history. Everything below about storage policies is reconstructed
from that history and **must be verified against production** before acting — the
queries are in the fix plan.

### 10.1 CRITICAL (pending production check) — the `company-notes` bucket may be readable across companies

`NotesView.tsx:190-193` calls `createSignedUrl` **in the browser with the
caller's own JWT**, on both the admin and the client surface. The policy in git
history is bucket-wide:

```sql
CREATE POLICY "Authenticated users can view company note attachments"
ON storage.objects FOR SELECT TO authenticated
USING (bucket_id = 'company-notes');
```

If that is still live, a client of company A can `list('note-attachments/<companyB-uuid>')`
and sign every attachment belonging to company B — and it also defeats
`visible_to_client`, because that filter exists only in the SQL query at
`NotesView.tsx:210-215`, never in the storage policy. Internal-note attachments
sit in the same folder.

**Verify first, then fix** by scoping the policy to `auth_company_id()` and moving
attachment signing behind a service-role route.

### 10.2 HIGH — Client DAM entitlement is a no-op (possibly by decision)

`platform/auth/damAssetAccess.ts:54-59` loads the caller's `company_id`, assigns
it, and then returns `null` with the comment *"Region and audience restrictions
removed by product decision."* The variable is dead. I verified the RPC does the
same: `20260407202000_simplify_client_dam_entitlements.sql` resolves
`v_company_id` at `:39-48` and **never references it again** — the asset filter is
`is_archived = false` plus UI filters only.

So every enabled client of every company can list and download every non-archived
asset. `company_dam_audiences` is written by nothing and read by nothing.

**This may be intentional** — the comment says it was a product decision. But
`CLAUDE.md` still states clients "browse DAM assets entitled to their company",
so code and documentation contradict each other. **This one needs your answer,
not a fix:** if all-partners-see-everything is the intent, delete
`company_dam_audiences` and correct the docs; if not, this is a live exposure of
regional-exclusive and unreleased material.

### 10.3 HIGH (pending production check) — public image buckets may be writable by any authenticated user

Per git history, `product-images` and `category-images` grant
INSERT/UPDATE/DELETE on `auth.role() = 'authenticated'` —
`3381d9d:fix_storage_policies.sql` explicitly *dropped* the admin checks. The
2026-05 migration removed only the SELECT/listing policies.

If still live: any client user can upload arbitrary content to a **public** bucket
on your Supabase origin (a phishing-page host), and can delete every product and
category image.

### 10.4 MEDIUM — Pipeline hygiene

- **Orphans on both ends.** `dam/assets/init/route.ts:175` inserts the asset row
  *before* any byte is uploaded, with rollback only in the browser's error
  handler — a closed tab leaves a permanent asset row with no version.
  `app/api/orders/delete/route.ts:126-130` deletes `order_documents` rows but
  never calls `storage.remove()`, so every PDF for a deleted order stays in the
  bucket and remains signable.
- **`complete` trusts a client-supplied `storagePath`** and never verifies the
  object exists (`:45-71` swallows the lookup failure), then sets
  `processing_status: 'complete'` unconditionally. Nothing checks the path starts
  with the asset id.
- **Filename sanitization is inconsistent.** `init` strips path separators but
  not `?`, `#`, `%`; the ≤5 MB path in `dam/assets/route.ts:569` uses the **raw**
  `file.name` with `upsert: true`. Paths are then interpolated into URLs without
  `encodeURIComponent`.
- **No server-side size or MIME enforcement** on upload; the browser uploads
  directly to storage. Files between 4.5 MB and 5 MB hit Vercel's body limit and
  fail with a generic error, per the code's own comment.
- **The job queue has no consumer.** `platform/queue/` is imported by nothing,
  the worker script points at a path that doesn't exist, and
  `supabase/functions/dam-upload` (which still enqueues) is invoked by nothing.
  Anything enqueued sits pending forever with no operator surface.
- **Deleting an asset destroys its download audit trail** —
  `dam_download_events.asset_id` is `ON DELETE CASCADE`, so the record of who
  downloaded a file is erased exactly when a leak investigation would need it.
- **No rate limiting on any delivery endpoint**, including
  `preview/resolve-batch` which mints up to 100 signed URLs per call.

## Part 11 — Build, infrastructure and operations

### 11.1 HIGH — There is no CI, and the test suite never runs before deploy

No `.github/` directory, no git hooks, no pipeline of any kind. Vercel deploys
whatever lands on `main`. **The entire deploy safety net is `next build`'s
TypeScript check** — which is at least real (`strict: true`, and
`ignoreBuildErrors` is not set).

The 15 Vitest files never run on the path to production, and ESLint never runs
either: `eslint` and `eslint-config-next` are installed, but **there is no ESLint
config file anywhere**, so `next build` prints "No ESLint configuration detected"
and skips it.

Combined with the absence of error monitoring, a runtime regression reaches
customers with no automated detection before, during, or after deploy.

**Fix:** a GitHub Action running `npm ci && npx tsc --noEmit && npm test`, plus
`.eslintrc.json` with `next/core-web-vitals`.

### 11.2 HIGH — No security response headers

`next.config.mjs` has no `headers()` block: no `X-Frame-Options`, no CSP, no
`Referrer-Policy`, no `X-Content-Type-Options`. HSTS comes from Vercel; nothing
else does.

The sharp edge is the referrer: password-setup links carry `?token=<live token>`
(`lib/passwordSetupTokens.ts:54`), and without `Referrer-Policy` that token leaks
in the `Referer` header to any third-party resource loaded on `/set-password`.
The admin panel is also framable, which matters for one-click destructive actions
(order delete, user delete, Stripe void).

### 11.3 MEDIUM-HIGH — Disaster recovery is not reconstructable

- **`env.example` documents 13 variables; the code reads 30.** Missing:
  `CRON_SECRET`, both Stripe keys, `SUPER_ADMIN_IDS`, four Amazon SP vars, seven
  ShipHero vars, six `S3_*` vars, `STORAGE_DRIVER`, `QUEUE_DRIVER`,
  `AUTH_PROVIDER`, `SUPABASE_STORAGE_BUCKET`, `RATE_LIMIT_LENIENT`,
  `NEXT_PUBLIC_BASE_URL`, `NEXT_PUBLIC_NETSUITE_ACCOUNT_ID`, and two NetSuite
  RESTlet ids. Most fall back to a default rather than failing, so a rebuilt
  environment comes up *half* working. It also documents `NETSUITE_REALM`, which
  the code never reads.
- **`scripts/db/dump.sh` defaults to `backups/` inside the repo, and `backups/`
  is not in `.gitignore`.** Running it with no argument drops a full production
  dump — every customer, price and address — where a stray `git add` would stage
  it. Nothing runs it, so there is also no application-owned backup;
  `docs/SECURITY_INCIDENT_RESPONSE.md` promises restoration from Supabase
  backups, which is unverified and never restore-tested.
- `.gitignore` covers `.env` and `.env*.local` but not `.env.production` /
  `.env.staging` / `.env.test`. **Git history is clean** — no secret was ever
  committed — but the gap is there.

### 11.4 MEDIUM — Operational gaps

- **Password-setup tokens are stored in plaintext**
  (`lib/passwordSetupTokens.ts:41-47` inserts the raw token as the primary key),
  while login codes are correctly stored as a SHA-256 hash
  (`20260517120000_auth_tokens.sql:36`). Any read of that table yields usable
  account-takeover links valid for 24 hours.
- **A magic-link object is logged on an error path.**
  `app/api/auth/verify-login-code/route.ts:159` logs `linkData?.properties`,
  which contains `action_link`, `hashed_token` and `email_otp`.
- **User email addresses are logged on normal paths** in at least five routes,
  accumulating PII in Vercel logs with no redaction or retention control.
- **The `refresh-reports` cron has no failure alert** — only `console.error`.
  That cron exists *because* the materialized views silently froze once already.
  If it starts failing, you are back in the same silent-staleness state with no
  signal. The Amazon FBA cron does email on failure; copy that.
- **Rate limiting covers 10 of 95 routes** — correctly the auth and email
  surface, and it fails closed. Uncovered: `users/create`, all DAM upload and
  download routes, all 19 NetSuite routes (which spend your OAuth quota), the
  report routes, and `stripe/request-payment` (which creates real invoices).
- **The image optimizer is exposed but unused.** `next.config.mjs:4-13` allows
  `*.supabase.co` — a wildcard across every Supabase project — while
  `next/image` is imported nowhere. That's the Next image-optimization CVE
  surface (Part 7) kept open for zero benefit.
- **The middleware matcher misses most API routes**, so a tab sitting on a DAM or
  Reports screen past token expiry gets 401s until the user navigates somewhere
  that refreshes the session. Not an authz hole — guards are per-route — but a
  real session-durability bug.
- **`supabase/functions/dam-upload` is orphaned**: invoked by nothing, excluded
  from typechecking (`tsconfig.json:26`), holds a service-role key, sets
  `Access-Control-Allow-Origin: '*'`, and may still be deployed.

## Part 12 — Documents and email

### 12.1 CRITICAL — Any admin can mint a password-setup link for any account, delivered anywhere

`app/api/users/send-reset-link/route.ts` takes `userId` **and** `userEmail` from
the request body (`:34`). It fetches the auth user by `userId` (`:61`) but
**never compares `authUser.user.email` to the supplied `userEmail`**. It then
mints a real 24-hour password-setup token for `userId` (`:73`) and sends it to
the body-supplied address (`:115`).

So `POST {userId: <any user's id>, userEmail: "attacker@example.com"}` returns a
working "set your password" link for that account, and the victim is never
notified. The sibling route `send-welcome-email/route.ts:168` does this correctly
— it sends to the canonical Auth email.

This requires an admin session, so it is privilege escalation between admins
rather than an anonymous hole. But combined with finding 1.3 — permissions are
not enforced server-side, so *any* admin reaches this route regardless of their
permission set — it means **any admin account is equivalent to every other
account, including the owner's.**

**Fix:** ignore `userEmail` entirely; send to `authUser.user.email`.

### 12.2 HIGH — Order emails can silently never send, and the timeline claims they did

Two separate defects that compound:

- **Send failures are invisible.** Confirmation emails are fired from the
  browser (`useOrderFormController.ts:23-46`) with `fetchWithAuth(...).catch(...)`.
  `fetch` does not reject on HTTP 500, so a server-side failure produces no log,
  no toast and no retry. They're fired inside a 1-second `setTimeout` before the
  redirect, so closing the tab quickly means they are never attempted at all. No
  table records email sends.
- **`/api/orders/notifications` writes "notification sent" to the order history
  without sending anything** — `:93-95` is a `// TODO: Integrate with email
  service`, and `:98-108` inserts the history row anyway, returning
  `success: true`. The order timeline asserts a notification that provably never
  left the system, which is an audit-trail falsification in exactly the scenario
  (a delivery dispute) where the timeline gets read.

Also: `lib/emailService.ts:73-79` uses `Math.min(exponentialBackoff,
retryAfter)`, so a Graph `Retry-After: 120` is discarded and all three retries
burn in ~7 seconds; and `messageId` is fabricated (`:138-141`,
`sent-via-graph-${Date.now()}`), so a non-delivery claim can never be traced in
Exchange.

### 12.3 HIGH — Preview and download are two different documents

The SLI an admin proof-reads on screen is produced by `lib/sliGenerator.ts`
(HTML string). The SLI they actually send is produced by
`lib/pdf/components/SLIDocument.js` (@react-pdf). They are independent
implementations reading the same record, and they disagree:

- **Weight.** The standalone form has no case-quantity field at all. The HTML
  path falls back to *units* × case weight; the PDF path falls back to *zero*. A
  20-case shipment truly weighing 180 kg previews as **2,160 kg** and downloads
  as **0.00 kg**. Either is a customs misdeclaration.
- **Checkboxes.** `lib/sliGenerator.ts:203-236` ignores `checkbox_states`
  entirely and hardcodes the answers — hazmat forced to "No", related-party
  forced to "Non-Related". An admin who ticks "Hazardous Material: Yes" proof-reads
  a document that says No. The PDF reads the stored state, so the two disagree on
  a regulatory declaration.
- **Consignee address.** The HTML builder hardcodes city/state/postal to empty
  strings, so box 11 prints `, , Germany, `.
- **Export date.** Order-based SLIs never capture `date_of_export`; both
  renderers stamp *today*, so reprinting the same SLI later prints a different
  export date.

**Fix:** render the preview from `SLIDocument` and delete `lib/sliGenerator.ts`.
This is one structural change that closes four findings.

### 12.4 HIGH — Declared customs values are recomputed, not recorded

Standalone SLI line values are `price_international × quantity` at render time
(`lib/pdf/api/sliDataFetcher.ts:77`, `lib/sli/buildStandaloneSLIData.ts:101`) —
the form never stores a value. So an Americas customer invoiced at Americas
pricing gets a customs declaration at international list price, against a named
invoice number. If `price_international` is null the line declares **$0.00**.

Related: `lib/sli/productAggregator.ts:53-73` merges lines by HS code and takes
`made_in` from the **first** member, so two SKUs sharing an HS code but made in
different countries merge into one line flagged with one origin — an origin
misdeclaration.

### 12.5 HIGH — Packing slips reprint differently after a catalogue change

`PackingSlipView.tsx:571,1242,1269` recomputes case counts as
`ceil(quantity / case_pack)` from the **live** product master, even though
`order_items.case_qty` was captured at order time and is what both order-detail
views and the SLI use.

Change a product from 12/case to 6/case and a shipped order's packing slip
reprints as **20 cases and double the weight** while the SLI for the same
shipment still says 10 — two documents in the same customs pack contradicting
each other. Missing `case_weight` silently prints `0.0 kg`.

The document is also dated with the render date (`:487`), not
`packing_slips.created_at`, and "Destination Country" is guessed from the
free-text address by a ~180-entry regex with a "last word" fallback (`:843-1074`)
while the structured `ship_to_country` column the SLI uses sits unused.

### 12.6 MEDIUM — Email recipient resolution can reach the wrong party

- `send-email/route.ts:130-134` falls back to `ship_to_contact_email` — the
  shipping-destination contact, often a warehouse or freight forwarder — for
  order confirmations containing line items and totals.
- `:84-91` resolves the recipient from `order.user_id` with **no check that the
  user still belongs to the order's company**. Reassigning a client to a
  different distributor (a normal admin action) redirects the old company's
  order emails to someone now working for a competitor.
- The one-time login code is placed in the **subject line**
  (`lib/emailTemplates.ts:605`), so it's readable on a locked phone's
  notification banner and retained in mail-gateway subject logs.

### 12.7 MEDIUM-HIGH — Unescaped values in the SLI HTML

`lib/sliGenerator.ts:96-124,154-162` interpolates forwarding agent lines, invoice
number, in-bond code, consignee name and address, instructions, HS code and
origin **without escaping**, and the result is rendered with
`dangerouslySetInnerHTML` on three admin pages. Two hazards: any `<` or `>` in an
address mangles the customs form (and script content executes in an admin
session), and `String.replace` with a string replacement honours `$&`, `` $` ``,
`$'` — a pasted note containing `$'` splices part of the document into another
cell.

Email bodies, by contrast, are **correctly escaped throughout** — see 12.8.

### 12.8 Verified correct

- **The sender lock is real and server-side.** `lib/emailService.ts:23,60` bakes
  the mailbox into the Graph URL as a module constant with no env or caller
  override. Callers cannot spoof `from`.
- **No CC or BCC anywhere.** `sendMail` builds `toRecipients` with exactly one
  address and supports no cc/bcc field, so cross-distributor address leakage
  through cc is structurally impossible.
- **HTML escaping in email bodies is complete.** Every user- or DB-supplied
  interpolation in `lib/emailTemplates.ts` and the notification routes goes
  through `escapeHtml`; the only bare interpolations are numeric.

## Part 7 — Dependencies and tooling (checked 2026-08-02)

`npm audit` reports **47 vulnerabilities: 4 critical, 18 high, 24 moderate, 1 low**.

- **`jspdf@3.0.3` — CRITICAL.** Local File Inclusion / path traversal (CWE-22)

**`xlsx@0.18.5` — verified low practical risk, recommend documented acceptance.**
SheetJS stopped publishing to npm at this version, so `npm audit` will report it
forever and no upgrade exists. But both reported vulnerabilities (prototype
pollution, ReDoS) are in the **parsing** path, and this codebase only **writes**:
`lib/reportExport.ts:35-53` uses `json_to_sheet` / `book_new` /
`book_append_sheet` / `XLSX.write`, and there is no `XLSX.read` anywhere in
`app/` or `lib/`. The product bulk-upload parses CSV, not xlsx; the other `xlsx`
matches are file-extension strings for DAM upload filtering.

So: accept it, record the reasoning, and add a note that the moment anyone adds
spreadsheet *import*, this must be revisited. Replacing it with `exceljs` is the
clean long-term option if you'd rather have a green audit.
