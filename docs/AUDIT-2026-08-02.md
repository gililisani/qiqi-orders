# Structural audit — 2026-08-02

Full-codebase audit triggered by finding two different "edit user" pages with
different capabilities. Five parallel read-only audits ran over: duplicate UI
flows, the API surface, the permission model, duplicated logic / dead code, and
data-access patterns.

Everything below was **verified by hand against the source** before being
written down. Claims that came back from an audit but did *not* survive
verification are listed in Part 6 so nobody re-raises them.

Excluded by prior decision: the known long files (`app/admin/dam/page.tsx`,
`PackingSlipView`, `OrderFormView`, `OrderDetailsView`, `companies/[id]/edit`)
are not flagged for size alone, and the accepted Supabase advisor warnings are
not re-litigated.

**Your instinct was right.** The two user-edit pages are not an isolated slip —
they're one instance of a pattern that repeats across the system: a feature gets
built, then a second version of it gets built somewhere else, and neither is
retired. There are 16 such pairs. Below that sits a more serious problem: the
permission system added in May is almost entirely cosmetic on the server.

## Part 1 — Fix first

These are live defects with business consequences, in the order I'd fix them.

### 1.1 Any logged-in user can read any order's customs paperwork (IDOR)

`app/api/orders/[id]/sli/data/route.ts:12-18` checks only that an
`Authorization` header is **present**, then passes the token to
`fetchOrderSLIData`. That helper (`lib/pdf/api/sliDataFetcher.ts:111-137`)
validates the token and then reads with the **service-role** client — no role
check, no company check.

Any authenticated distributor can request `/api/orders/<any-order-id>/sli/data`
and receive another company's Shipper's Letter of Instruction: consignee,
addresses, declared values, HS codes. The sibling route
`app/api/orders/[id]/sli/route.ts:26-54` *does* check company ownership — that's
what this one should look like.

The endpoint is live (used by `app/admin/orders/[id]/sli-preview/page.tsx:62`).

**Fix:** `requireAuthenticatedUser` + `assertOrderAccess`, or `requireAdmin` to
match the rest of the SLI family.

### 1.2 Every new user is created with zero permissions

`app/api/users/create/route.ts:79-85` calls the `create_client_profile` RPC with
name/email/company/enabled only. The RPC
(`supabase/migrations/20260514120000_user_lifecycle_rpcs.sql:33-34`) doesn't
write `permissions`, and the column defaults to an empty array
(`supabase/migrations/20260526120000_user_permissions.sql:33,36`).
`DEFAULT_CLIENT_PERMISSIONS` in `lib/permissions.ts:47` is referenced only by the
edit page's form state — never by any creation path.

So every client user created since the May permissions migration lands with `[]`,
logs in, and gets bounced to `/forbidden` (`app/client/layout.tsx:182-192`). The
account only starts working if someone happens to open `/admin/users/[id]/edit`
and save, which re-grants defaults as a side effect (see 1.6).

Same bug for admins: `app/api/admin/create/route.ts:88-95` inserts without
permissions, while `app/admin/admins/new/page.tsx:97-103` tells the operator
"This admin will have full access to the system." The new admin gets an empty
sidebar instead.

**Fix:** write the defaults at creation time (or change the column default).

### 1.3 Permissions are not enforced on the server

`requireWithPermission` exists in `platform/auth/guards.ts:90` and is called by
exactly **one** route out of 95: `app/api/client/performance/route.ts:24`.
Everything else stops at "is this an admin" / "is this a client".

Meanwhile the admin area has **no route guard at all** — `app/admin/layout.tsx`
filters nav items but never redirects, unlike `app/client/layout.tsx:182-193`.
So an admin restricted to, say, DAM reaches every admin page by typing the URL,
and every admin API answers them. Today `users:manage`, `admins:manage`,
`companies:manage`, `netsuite`, `settings` and `reports` have no server-side
effect whatsoever.

Worse, permission writes happen **from the browser**:
`app/admin/admins/[id]/edit/page.tsx:79-88` updates `admins.permissions`
directly, and the RLS policy
(`supabase/migrations/20260515120000_tier1_rls_overhaul.sql:68-71`) only asks
"are you an admin". Any admin can grant themselves everything.

**Fix, staged:** (a) port the client layout's redirect guard into the admin
layout; (b) move the two permission writes behind guarded API routes; (c) convert
route families to `requireWithPermission`.

### 1.4 Disabling a user does not lock them out

`app/api/user-profile/route.ts:91-102` returns the profile and role regardless of
`enabled`, and `app/client/layout.tsx:153` checks only the role. Supabase Auth
doesn't know about `enabled`, so a disabled user still authenticates and still
gets the portal shell.

Most data comes back empty because `auth_company_id()` requires `enabled = true`,
so it *looks* like an empty account rather than a revoked one — but the session
is real, and any table whose policies don't check `enabled` stays readable.

**Fix:** reject `enabled !== true` in the layout and in `/api/user-profile`.

### 1.5 Target-period progress is never recalculated when an order completes

Two callers hit `/api/target-periods/recalculate` with plain `fetch` and no
Authorization header:
`app/components/shared/orderDetails/useOrderDetailsController.ts:222-226` (fires
when an order flips to/from Done) and
`app/admin/companies/[id]/historical-sales/page.tsx:97-101`.

The token lives in localStorage, not cookies, so `requireAdmin` rejects both.
Both callers swallow the failure — one logs, one has an empty catch. The stored
`current_progress` silently stops tracking reality while the UI reports success.
This is the same shape as the missing `order_history` writes that hid $265k of
Done orders in July.

**Fix:** use `fetchWithAuth`, and surface failures instead of swallowing them.

### 1.6 The permissions editor silently re-grants defaults

`app/admin/users/[id]/edit/page.tsx:72-74` and
`app/admin/admins/[id]/edit/page.tsx:53-55` both do "if the stored array is
empty, show the defaults". Deliberately removing every permission is therefore
not representable: reopen the page and the boxes are ticked again, and saving any
unrelated field re-grants `['orders','dam']` — or, for admins, all eight
permissions including `admins:manage`.

**Fix:** use the stored array verbatim once loaded; seed defaults only on create.

### 1.7 Changing an admin's email or password silently does nothing

`app/admin/admins/[id]/edit/page.tsx:91-101` calls
`supabase.auth.admin.updateUserById` from a **browser** page using the anon key.
That API needs the service-role key, so it always fails — and the result is never
checked, so the page reports "Admin updated." The profile row changes; the actual
login credentials don't, so the user's login email silently diverges from their
displayed email.

The same unchecked call was copy-pasted into all three user-edit pages
(`app/admin/users/[id]/edit/page.tsx:107-112`,
`app/admin/companies/[id]/users/[userId]/edit/page.tsx:86-91`).

**Fix:** one guarded API route doing profile + auth atomically.

### 1.8 Client "delete order" calls an endpoint that doesn't exist

`app/components/client/ClientOrderDetailsView.tsx:160` does
`DELETE /api/orders/${orderId}`. There is no `route.ts` at that path — only
`documents/` and `sli/` children. The real endpoint is `/api/orders/delete?orderId=`,
used correctly by the admin controller (`useOrderDetailsController.ts:518`).
Deleting from the client portal always fails with "Failed to delete order."

Three different rules for this one action also coexist: the API allows any role
on Cancelled only; the shared controller says Cancelled-or-Draft with Cancelled
admin-only; the client view shows the button on Cancelled.

### 1.9 Clients can edit packing slips

`app/components/shared/PackingSlipView.tsx:840` gates editing on order status
only — `['Ready','Done'].includes(order.status)` — with no role check, even
though both pages pass a `role` prop. On `/client/orders/[id]/packing-slip` a
distributor gets working Create/Edit affordances on a shipping document
(invoice number, NetSuite reference, notes).

**Fix:** `role === 'admin' && [...]`.

### 1.10 Order writes don't check that anything was written

`app/components/shared/orderForm/useOrderFormController.ts:251-275` updates the
order, deletes its items and re-inserts — with no `.select()` and no row count.
supabase-js returns `error: null` when RLS filters an UPDATE to zero rows, so a
blocked write is indistinguishable from a successful one. If an admin moves an
order to Processing while a client has the form open, the client's save no-ops
and the UI redirects as though it saved.

### 1.11 New companies are invisible to target-based reporting

`app/admin/companies/new/page.tsx:183-215` inserts 26 columns but omits
`contract_execution_date`, `contract_duration_months` and `contract_status`, and
has no territories or target-periods editors — all of which exist only in
`app/admin/companies/[id]/edit/page.tsx:388-427`.

Since `target_periods` is what drives `lib/companyPerformance.ts`, every company
onboarded through the create form is absent from Company Performance until
someone remembers to reopen it in Edit.

### 1.12 Bulk-uploaded products get wrong support-fund behavior

`app/admin/products/bulk-upload/page.tsx:128-145` writes 13 columns. It never
writes `category_id`, `qualifies_for_credit_earning`, `hs_code`, `made_in`,
`case_weight` or `out_of_stock` — the words don't appear in the file at all,
while both single-product forms write 18 columns.

Consequences: imported SKUs have no category (so they don't group in the order
form), no HS code or weight (SLI and packing-slip fields), and fall to the DB
default for credit earning — which feeds support-fund accrual
(`AdminOrderFormView.tsx:447`) and therefore money.

## Part 2 — The duplication pattern

This is the direct answer to "why are there two edit-user pages". There are 16
of these. The ones that matter:

**Two "edit user" pages.** `app/admin/users/[id]/edit/page.tsx` (294 lines) has
permissions *and* company reassignment.
`app/admin/companies/[id]/users/[userId]/edit/page.tsx` (231 lines) has neither.
Both are live; neither links to the other. The Users list routes to the capable
one; `app/admin/companies/[id]/page.tsx:537` — the Edit button on every user row
of a company, the path you'd naturally use — routes to the crippled one. They
even send different reset-link payloads, so the two produce different emails.

**Two "create user" pages** (`app/admin/users/new`, `app/admin/companies/[id]/users/new`)
— these at least both post to `/api/users/create`.

**SLI is two entities with two form systems and three preview pages.** Order SLIs
live in `slis`, standalone SLIs in `standalone_slis`. The standalone form
(`SLIFormFields.tsx`, 686 lines) exposes all 19 checkbox groups; the order form
(`CreateSLIModal.tsx`) hardcodes five of them with no setter
(`CreateSLIModal.tsx:64-82`). Order SLIs get no SLI number and **never appear in
the SLI documents list**, which queries `standalone_slis` only
(`app/admin/sli/documents/page.tsx:23-26`) — customs paperwork issued against
orders is untracked. Three preview pages render it three ways, one of which
(`/admin/sli/preview`) has zero references anywhere.

**Order create/edit is forked admin↔client**, ~2,500 lines, with eleven helper
functions duplicated character-for-character including `getProductPrice`,
`getOrderTotals` and `getSupportFundTotals`. Any pricing change has to land in
two files or admin-entered and client-entered orders price differently. Both
sides also declare `visible_to_americas`/`visible_to_international` and use
neither, so region visibility silently does nothing.

**Order details / list / documents / history are each forked** the same way —
`AdminOrderHistoryView` and `ClientOrderHistoryView` are ~99% identical and the
client file's own comment admits the visual is identical.

**Company create vs edit** duplicate a 26-column mapping character-for-character
(see 1.11). **Product create vs edit vs bulk-upload** are three payloads (see
1.12). **DAM locale/tag creation exists twice** with different validation — the
inline path in `app/admin/dam/page.tsx:3316` uses `prompt()`/`alert()` and skips
the duplicate check the settings page has. **Category ordering is editable two
ways** with incompatible semantics: a curated `sort_order` set in the edit form
is wiped the next time anyone saves the drag-and-drop reorder page.

**Three admin-auth implementations coexist**: `requireAdmin`,
`createAuth().requireRole`, and hand-rolled `admins` lookups — the last is where
the IDOR in 1.1 slipped through. Plus ~18 hand-rolled service-role clients
instead of `createServiceRoleClient()`.

## Part 3 — Needs your input before anyone acts

Ten client-facing tables have **no RLS policy in any migration**:
`company_notes`, `note_attachments`, `order_documents`, `order_history`,
`packing_slips`, `company_territories`, `categories`, `incoterms`,
`payment_terms`, `highlighted_products`. All ten are queried directly from the
client browser.

Migrations aren't the whole truth — policies added through the Supabase dashboard
don't appear in the files, and I have no production credentials here. Two very
different realities are possible:

- **RLS on, no policy** → clients silently see empty notes, no documents, no
  order history, no territories, blank incoterms and payment terms.
- **RLS off** → those tables are readable by any authenticated session, which is
  a data-exposure problem instead.

Run `scripts/db/audit-rls-state.sql` in the Supabase SQL editor and send me the
output. The fix is completely different depending on the answer, so this is the
one item I'd rather not guess at.

## Part 4 — Consistency debt

Not urgent, but it's what turns a one-line change into a three-file change and
lets copies drift apart.

- **Order status has six sources of truth** — two colour maps
  (`components/qq/status-badge.tsx:31`,
  `admin/reports/_components/StatusFunnelChart.tsx:12`) that disagree with each
  other, a third dead one, `STATUS_ORDER`/`COMMITTED_STATUSES` in the executive
  report route, and ~20 open-coded membership tests.
- **Currency formatting has ten implementations** — some 0-decimal, some
  2-decimal, one emitting `US$` — plus ~20 raw `.toFixed(2)` sites that lose
  thousand separators, so the same amount renders `$12,345.67` in one place and
  `$12345.67` in another. `lib/formatters.ts:31` is the canonical one.
- **Date formatting has eight local `formatDate` copies** in three formats, plus
  ~25 bare `toLocaleDateString()` calls that render `dd/mm/yyyy` for non-US
  browsers. Some pin UTC, some don't — those can be off by a day.
- **`lib/csvExport.ts:173`** wraps CSV fields in quotes without doubling embedded
  quotes, so a name containing `"` corrupts the NetSuite import file.
  `lib/reportExport.ts:96` does it correctly.
- **`userHasPermission` (`lib/permissions.ts:74`) has zero callers** despite its
  own doc saying "use this everywhere". Consequence: the `SUPER_ADMIN_IDS`
  override works for API routes but not for nav filtering or client-side gating —
  and it's parsed twice, in two places, with different semantics.

## Part 5 — Delete list

Dead code, verified zero importers. Two items are actively dangerous:

- **`lib/emailTemplates.ts:272` `welcomeUserTemplate`** emails a **plaintext
  temporary password**. Every live caller uses `welcomeEmailTemplate` (setup
  link). Delete before someone wires it up.
- **`lib/auth-utils.ts`** — a complete second auth implementation gating on a
  `users` table with a `role` column that isn't the live model.

The rest: `app/components/reports/` (7 components, sole reason `apexcharts`,
`react-apexcharts` and `deepmerge` are still dependencies), `platform/queue/`,
`lib/pdf/utils/*`, `lib/pdf/constants.ts`, `lib/pdf/generators/sliGenerator.ts`,
`app/components/shared/ContractInfo.tsx`, `app/components/ui/OrderStatusBadge.tsx`,
`app/configs/charts-config.ts`, `app/components/ui/TopNavbar.tsx`.

Nine dead API routes are still deployed with service-role write paths:
`/api/orders/auto-save-draft`, `/api/orders/complete`, `/api/orders/notifications`,
`/api/dam/assets/[id]/versions`, `/api/dam/queue/metrics`,
`/api/users/send-welcome-email`, `/api/fulfillment/shiphero/register-webhook`
(possibly deliberate ops endpoint), `/api/netsuite/orders/create` (410 stub),
`/api/netsuite/products/sync` (501 stub). `auto-save-draft` also carries a
**wrong copy of the support-fund math** (`route.ts:157-165` omits the
`qualifies_for_credit_earning` filter both form views apply), so reviving it
would write inflated `credit_earned`.

`/dev/components` and `/dev/layout` are design galleries with no layout guard and
no middleware coverage (`middleware.ts:28-37`) — publicly reachable in
production. No data, but internal UI.

## Part 6 — Raised but not real

Checked and dismissed, so they don't come back:

- **Dashboard outstanding-balance treats null as $0** — it does skip unknown
  balances (`app/client/page.tsx:270-276`), and the comment documents
  under-reporting as the deliberate choice. Working as intended.
- **Admin orders list status filter disagrees with results** —
  `AdminOrdersListView.tsx:152` appends `'Draft'` on purpose, with a comment.
- **Public `/api/auth/*` routes are unguarded** — intentional and rate-limited;
  `check-user` deliberately buckets unknown emails to prevent enumeration. Both
  webhooks authenticate by secret. Cron routes check `CRON_SECRET` and fail
  closed when it's unset.
- **Permission key typos** — none. Every key used in the layouts and routes
  exists in `lib/permissions.ts`.
- **Packing slip pages duplicated** — both are thin wrappers around the shared
  `PackingSlipView`. The problem there is the missing role gate (1.9), not a
  second implementation.
